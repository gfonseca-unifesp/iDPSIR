Tutorial · iDPSIR

Finding your way around iDPSIR

iDPSIR is an R/Shiny app for building and reading causal networks under the DPSIR model — Driver, Pressure, State, Impact, Response — a framework environmental managers use to trace how a human activity turns into an environmental pressure, changes a system's state, causes an impact, and is met with a response. This walks through opening the app, filling in the wizard, and reading what each tab is telling you. No graph-theory background required.

Before you start

Running the app

Pick whichever of these matches what you're doing today — a one-off look, or ongoing work you'll want to keep and update.

Quick look, no setup

Runs the current main branch straight from GitHub. Nothing is kept on disk after you close R.

shiny::runGitHub("iDPSIR", "gfonseca-unifesp", "main")

Keep a working copy

Clones the repo so you can update it later and it opens cleanly as an RStudio project.

git clone https://github.com/gfonseca-unifesp/iDPSIR.git
cd iDPSIR

Then in RStudio: File → Open Project…, and run:

shiny::runApp()
Requires R ≥ 4.1. Missing packages are installed automatically on first run — no manual install.packages() step needed. Both routes open a browser tab with the app running locally — nothing is sent anywhere else.

Model

This is the DPSIR schema — the five categories, the order they connect in, and how each is drawn. The default is what almost everyone should use as-is; it's shown here so the colors and shapes below make sense everywhere else in the app.

CategoryOrderConnects forward toRole
Driver1Pressure—
Pressure2State—
State3Impact—
Impact4Response—
Response5Driver, Pressure, State, Impactfeedback

Response is marked feedback: it's the only category allowed to connect back to earlier ones — the loop that makes a response actually change the system it responds to. "Advanced" options here let you swap the color palette or add extra levels, but most projects won't need them.

Nodes

Add opens a form for one node at a time; Edit selected and Remove selected work on the row you've picked in the table.

FieldWhat it means
idA short, unique code (e.g. P1) used everywhere else to refer to this node.
labelThe human-readable name shown on the graph and in tables.
dpsir_categoryDriver, Pressure, State, Impact or Response — sets the shape, color and position on the graph.
subsystemOptional grouping (e.g. "Fisheries", "Water") — lets you filter the Graph tab down to one part of the network.
uncertaintyOptional number in [0, 1], default 0.5 — how confident you are this node is described correctly (0 = very confident, 1 = very uncertain). Thickens the node's border on the graph. Not read by any calculation, purely a visual/documentation aid.
controllabilityOptional number in [0, 1], default 0.5 — how much a manager can influence this factor directly (0 = not at all, 1 = fully). Not read by any calculation.
descriptorOptional — a short, plain-language description of what this factor represents. Purely documentation: not read by any calculation, just there so someone reading the network later (including a future you) doesn't have to guess what a node means.

The form shows a guide (half-life, build-up); see Self-regulation. Only used by the Scenarios tab's optional temporal simulation.
growth_rateOptional number, default 0. This factor's own exogenous trend per time window (e.g. population growth), independent of any edge — also only used by the temporal simulation.

The factor's initial level in its own units (e.g. 100 t of stock) and its typical variation — a standard deviation, or a coefficient of variation that the form converts. The model works in standard deviations; with these two numbers, results, thresholds and pushes can be read and entered in real units (the Scenarios tab then offers "or, in units" next to each push, and the temporal simulation shows a Change relative to initial values table).

Used to prioritize Impacts on the Scenarios tab.

4

Edges

An edge is a directed link, from one node to another — it has to follow the connection order from the Model step (a Pressure→Impact edge, skipping State, will be flagged in Review).

FieldWhat it means
StrengthHow many standard deviations the target changes when this factor changes by one (a standardized path coefficient, beta). No data? Pick a class — Weak (0.15), Moderate (0.45, the default) or Strong (0.80). With data, choose "I have a value" and enter beta — or r² instead (the form uses |beta| = √r²), optionally with the sample size n. Drawn as line thickness on the graph.
Uncertainty rangeLowest and highest plausible strength. Optional: otherwise it comes from r² and n, or from the class (Weak 0–0.3, Moderate 0.3–0.6, Strong 0.6–1.0). Used only by the confidence readings, never to shrink the effect. A wide range is drawn dashed.
interaction_typepositive (the link increases its target) or negative (it decreases/mitigates it) — colors the edge red or green and appears in its tooltip.
evidence_typee.g. observational, expert_assessment, monitoring — where the link comes from, shown on hover.
referenceOptional — a DOI, URL, or plain citation backing this specific link. Shown on hover and, if you check "Edge references" on the Report tab, listed in a References section so a reader can trace any prediction back to its evidence.
What you need to enter. Only the structure (nodes with their category, edges) and the sign of each edge are required. Everything else has a default, and the network runs with them — the results are then qualitative, and the Review step and the report say how many edges rely on a default. Fields that do the same job replace each other; fill in one: strength = beta, or r², or a class (default Moderate); uncertainty = a range, or r² with n, or the range of the class. The effect of a scenario is the product of the strengths along each causal path, summed over paths — a response far from an Impact is naturally attenuated. If the network's feedback loops would amplify without bound, Build is blocked and the message names the edges on the loop.
5

Review and build

A summary ("6 nodes, 7 edges") plus a plain-language list of anything invalid — usually an edge that skips a category. Fix those, then press Build/Rebuild graph. This is also the button to press again any time you go back and edit nodes or edges — the Explore tabs always show the graph as of the last build, not your unsaved edits.

Nothing updates automatically. Changed a node's category after building? Rebuild before trusting what Explore shows you.
Reading the network

The Explore tabs

Once the graph is built, four tabs cover everything from the visual layout to a downloadable report. They all read the same built graph — nothing here edits your nodes or edges.

Graph

The main view: every node placed in a column by DPSIR category, with arrows showing the direction of each effect. Controls live in collapsible boxes down the left — click a section's title to expand it — while the graph and its legend take up the wider space on the right.

Scenarios

Tests "what if we implemented this response, and how hard?" — without touching your saved network. Two independent "pushes" you build side by side: what's pushing the system to get worse, and how you're responding to it.

GraphScenariosMetricsReport
Pressure scenariocheckbox + slider each

Optional. One row per Driver/Pressure node — turn on any combination you expect to worsen, and how strongly. A push of 100% is one standard deviation of that factor; the slider goes up to 500%, and a factor with a typical variation (SD) also takes the push in its own units ("or, in units").

Response scenariocheckbox + slider each

One row per Response node — turn on any combination you want to test, and how strongly each is implemented.

Apply scenariobutton

Runs both scenarios and shows "Is the response enough? (sufficiency)" — for each Impact, how much the pressure scenario worsens it, how much the response scenario mitigates (or, sometimes, worsens) it, whether that's enough to neutralize the worsening, and how strong the response would need to be if not. The effect is the product of the edges' strengths along each causal path, summed over paths.

How confident is that, response by response?table

Every response in the network, evaluated alone at full strength against the same pressure scenario: the percentage of simulations — resampling every edge's strength within its uncertainty range — in which that response alone neutralizes each Impact.

State triggerstable, only with thresholds

Each State with a threshold: its deviation under the pressure alone and with the response, whether its trigger is open before and after, and whether the response closes it. A closed trigger holds back everything beyond that State — which is why an Impact can be neutralized "by the trigger" rather than by mitigation, and why Reach also reports how many factors this scenario actually reaches.

Impact prioritizationtable + chart

Which Impact to act on first. Relevance = value v × importance D (how much the pressure scenario moves that Impact, relative to the most affected one) × reliability (how often that prediction keeps its sign when every strength is resampled within its range). Priority = relevance × gap (the share of the worsening the response scenario leaves uncovered — 0 when neutralized). An Impact the pressure doesn't worsen reads "Not affected". Downloadable as CSV and included in the report.

Reachtable

How many factors — and how many Impacts — the active response(s) can touch by following the network's links. Independent of the sufficiency reading above: it's a plain count of what's reachable, always available.

Show temporal simulation across discrete time windowsoptional

Runs the same two scenarios forward window by window instead of reading a single instant — useful when a response might, windows later, become a new pressure itself (see the worked example). Pressure and response each run as Added every window (default) or Applied once and held (window 1 only; the level it creates fades only through self-regulation). Simulation length: until the response neutralizes the Impact (default, up to 50 windows — it stops at the first window in which every Impact the response reaches, and that the pressure has already worsened, is at or below zero; otherwise it says "Not neutralized within N windows") or a fixed number of windows. Optional: a neutralization tolerance (default 5% of the baseline, which only labels the table as "Neutralized (relative)"), and a baseline without any response (ignoring Impact → Response links). With a thresholded State, a Trigger criterion: accumulated State level (default — has the State deviated beyond the critical point, adding up every window?), load arriving at the State (did what arrived in this window pass the limit?), or compare both; a table then shows each trigger open or closed window by window. Factors with an initial level get a Change relative to initial values table, in their own units, with the window in which a threshold was crossed. A progress indicator shows "Window X of N" while it computes. Shows a table of how each Impact changes window by window, with a Verdict per row (see Reading the Verdict), and a chart — one panel per Impact, dashed baseline vs. solid Net, each Net point colored by that window's Verdict, with the neutralized zone (Net ≤ 0) shaded — downloadable as PNG or SVG and included as a figure if this scenario is added to the report.

Read this before your first network

Modeling convention: orienting nodes and reading signs

The app never guesses whether "more" of a factor is good or bad — that's a decision you make when you name a node and sign its edges. Get this right and consistent, and every reading downstream (sufficiency, confidence, temporal Verdict, the temporal chart's colors) is trustworthy. Get it inconsistent, and a table can report the opposite of what you intended without any error or warning — the app validates that a sign is positive or negative, not that it means what you think it means.

Step 1 — orient each node: decide what "more" means

CategoryWhat "more" meansExample
Driver / PressureMore force or stress — more is more pressure.fishing effort, population growth
StateThe condition itself, measured in its natural/good sense — more is a better condition.Coral cover, Fish stock, Biodiversity — never Coral degradation or Fish stock decline
ImpactThe problem or damage itself — more is worse.Catch decline, Fisher income loss

State is the one category worth pausing on: name it as a neutral measurement, not as the problem it's usually associated with. A State named after a problem ("Fish stock decline") quietly bakes a sign assumption into the node itself — one that can silently drift out of sync with whatever the edges actually say.

Step 2 — the edge's sign is mechanical

Once every node is oriented, signing an edge is a small, mechanical question: when the source goes up, does the target go up (positive) or down (negative)? Nothing about "good" or "bad" enters at this step — that judgment already happened in Step 1, when you chose what "more" means for each node. With the standard orientation above, the connections this app's schema allows always sign the same way:

LinkSignWhy
Driver → Pressurepositivemore force → more pressure
Pressure → Statenegativethe pressure reduces the good condition
State → Impactnegativemore good condition → less of the problem
Response → Driver / Pressurenegativethe response reduces the force/pressure
Response → Statepositivethe response improves the condition
Response → Impactnegativethe response reduces the problem
Golden rule: the same node uses the same orientation on every one of its edges — incoming and outgoing alike. Almost every sign mistake in a DPSIR network comes from breaking this rule: signing a State as "good" on its incoming edge and as "the problem" on its outgoing edge (or vice versa). See sample_nodes.csv/sample_edges.csv's own history for a worked example of exactly this mistake, and the Mangi network below for what a consistent, neutral State looks like in practice.

Reading the Verdict (temporal simulation)

With an Impact oriented as the problem (Step 1 above): zero means no deviation from doing nothing, a positive value means worse, and a negative value means better than doing nothing — the response didn't just help, it pushed the factor past neutral. Each simulated window compares the baseline (pressure only) against the net (pressure and response together, the same "Net" column the sufficiency table above already uses for this quantity) and labels the Impact's net value accordingly:

VerdictConditionMeaning
Neutralizednet ≈ 0the response's benefit exactly offsets the pressure's worsening
Improved beyond neutralnet < 0the response did more than enough — the factor is better than if nothing had happened at all
Neutralized (relative)0 < net ≤ tolerance × baseline, and not growingpractically neutralized: within the tolerance (default 5%) of the baseline and not getting worse from the previous window. Only a label — "until neutralized" still waits for net ≤ 0
Partial0 < net < baselinestill a problem, but smaller than it would be without the response
Failure/worsenednet ≥ baselineas bad as, or worse than, no response at all

The Verdict is judged by sign, not by how large a number is — a response that overshoots into strongly negative territory is Improved beyond neutral, never Failure/worsened, no matter how big that negative number gets. This also keeps the label consistent with the temporal chart's color: green always means neutralized or better (net ≤ 0), so a row marked worse can never show up green.

Temporal simulation

Self-regulation: how a factor recovers on its own

self_regulation (0–1, default 0.5) is the share of a factor's deviation that fades by itself each window, independently of the network: 0 = nothing fades and everything that arrives accumulates (a stock with no replenishment, a persistent contaminant); 0.3 = 30% of the deviation fades each window (a population rebuilding, a habitat regenerating); 1 = no memory, the factor only reflects what arrives in the current window.

Each window: new value = (1 − self_regulation) × previous value + what arrives through the edges + the push.

Example — fishing effort (P) → fish stock (S) → catch decline (I), with strengths 0.7 and 0.6 (both negative) and a pressure of 1 standard deviation:

CaseWindow 24812
Ongoing pressure, self-regulation 0 everywhere — fish stock−0.70−4.20−19.6−46.2
Ongoing pressure, stock recovers 30% per window — fish stock−0.70−1.53−2.14−2.29 (settles at −0.7 ÷ 0.3 = −2.33)
Ongoing pressure, self-regulation 1 everywhere — fish stock−0.70−0.70−0.70−0.70 (same as the static reading)
One-off pressure, stock recovers 30% per window — fish stock−0.70−0.34−0.08−0.02 (back to normal)

Under a constant load, a factor settles at load ÷ self-regulation: a contaminant with self-regulation 0.05 accumulates up to 20 times what arrives each window, which is how a small per-window pressure can still cross a threshold through accumulation.

Self-regulationHalf-life of recoveryBuild-up at equilibriumTypical of
0.0513.5 windows20×contaminant in sediment
0.106.6 windows10×reef recovery, long-lived species
0.301.9 windows3×short-cycle fish stock
0.50 (default)1 window2×water quality that renews quickly
1—1×monthly income, catch in the window

What makes an Impact converge is the chain's self-regulation; the response mode decides the effort; the stop criterion says in which window the problem was solved.

Three networks, three sizes

Example networks

Three ready-to-load networks ship with the app, each making a different point. Start with whichever matches what you need right now — a five-minute orientation, a real published network, or the deepest example in the app (covered in full in the next section).

Fisheries — the smallest possible loop

Five nodes, five edges, one closed feedback loop: Coastal tourism growth (Driver) → Overfishing (Pressure) → Fish stock (State) → Fisher income loss (Impact) → Fishing quota policy (Response) → back to Coastal tourism growth. No subsystem filters, no temporal simulation needed to see what's going on — this is the network to open first, just to get oriented with the wizard and the Graph/Scenarios tabs before anything else adds complexity. Turn on Coastal tourism growth as pressure and Fishing quota policy as response, both at 100%: because it's a genuine loop, the response's Reach covers all 4 other factors — but with this network's edge strengths (three Strong links along the pressure chain, a Moderate Impact → Response link and a Weak Response → Driver link), a single response this far from the Impact isn't remotely enough on its own (Fisher income loss needs 667% strength to neutralize a 0.495 worsening with only -0.074 of mitigation) — a quick, honest first look at what "Strength needed" means when a response is badly outmatched.

Mangi et al. 2007 — a real published network, and a real bug it caught

18 nodes, 31 edges — coral-reef fisheries management in a real paper (Mangi, S.C., Roberts, C.M., & Rodwell, L.D. (2007). Reef fisheries management in Kenya: Preliminary approach using the driver-pressure-state- impacts-response (DPSIR) scheme of indicators. Ocean & Coastal Management, 50(5-6), 463-480, doi:10.1016/j.ocecoaman.2006.10.003). This is the network that caught a real, reproducible bug during development: the older equilibrium-based reading this app used to show (removed since, see Scenarios above) reported Gear restrictions as making Reef ecosystem degradation worse — the wrong sign for a response explicitly meant to protect the reef. Loading this network and applying pressure from Coastal population growth + Market demand for reef fish, with Gear restrictions as the response, shows the corrected sufficiency reading: Reef ecosystem degradation reads worsening 0.03 / mitigation -0.069 / net -0.039, Yes, neutralized at 44% strength — mitigation with the right sign, not the wrong one. It's also a good look at a densely cross-linked network: this single response's Reach covers 14 of the other 17 factors, because Responses here loop back into several Drivers, Pressures and States at once, not just the one Impact they're aimed at.

This network is also the concrete illustration of the modeling convention above: every State is a neutral measurement — Fish stock, Coral cover, Biodiversity — never pre-judged as "decline" or "degradation", so Pressure→State and State→Impact are both negative and Response→State is positive, exactly the standard signing from Step 2 above.

Everything above is easier to follow with a real network in front of you. This one is adapted from a real paper — Gnanapragasam et al. 2026, Marine Policy, on artisanal fisheries in northern Sri Lanka — and walks through both readings: the static sufficiency check, and the optional temporal simulation that shows a response's own success quietly eroding over time, for reasons that have nothing to do with the response itself.

Treat this network the way you'd treat any DPSIR diagram you build yourself: one useful, structured lens on the system, worth checking against expert judgment before acting on it.

The story

After the 2004 tsunami and, later, the end of a long civil war, aid programs replaced fishing boats and gear lost by coastal communities in northern Sri Lanka. The paper is explicit about what that aid was for: compensating fisher income loss — the human cost of a shrinking catch — not growing the fleet. This network takes that at face value: both aid programs (Response) link directly to Fisher income loss (Impact), the thing they were actually designed to fix — and to nothing else.

Everything else in the network is driven by the pressure side instead. Fishing effort — pushed by population growth, demand growth, and the number of fishers and boats (the latter given its own small standing growth_rate, since the paper observes this trend without pinning down a cause) — does two things: it depletes the fish stock (feeding catch decline, income loss, and conflict with Indian fishermen), and it drives fleet motorization directly, independent of any aid program. That growing motorized fleet then compounds catch decline and conflict further, on top of what the fish-stock route already causes, and separately accelerates the decline of traditional (non-motorized) fishing and the culture built around it. The result: the aid's own causal footprint and the pressure's causal footprint don't overlap anywhere in this network.

A deliberate exception to the neutral-State default. Fish stock follows the standard convention (Step 1): neutral, more is better, so both its edges are negative. Fleet motorization does not — it's oriented the other way on purpose (more motorized capacity is itself more pressure on the system), so both its edges are positive instead. This is still fully consistent with the golden rule: each State uses one orientation across all of its own edges, in and out — Fleet motorization just picked "more is worse" instead of "more is better." Not every State has to default to "more is better"; what matters is that the choice, whichever it is, holds for that node's every edge.

Both aid programs (post-tsunami and post-war) link to exactly one factor — Fisher income loss — with the post-war program weighted slightly stronger, reflecting it being the larger of the two efforts. Neither aid program has any other link, direct or indirect: everything else in the network (fishing effort, the fish stock, fleet motorization, and the four other Impacts) is completely outside what either program can reach, by construction.

Is the response enough?

The example savepoint already has this configured: a pressure scenario with Coastal population growth and Fish demand and consumption growth at 100%, and a response scenario with both Post-tsunami aid and Post-war aid at 100%. In Scenarios, click Apply scenario.

Several are at or above 1, and the Review step warns that the edges arriving at three factors would "explain" more than 100% of their variation — a sign that, read as standardized coefficients, some of them are on the high side. Only one row has a non-zero Mitigation. Fisher income loss is the response's sole target. Every other Impact reads Mitigation exactly 0.000, not because the response fails against them, but because it has no causal path to them at all — worsening carries straight through as Net, untouched.

Notice also that Fisher income loss has no worsening at all in this reading. That is the Fish stock trigger at work (see A threshold worth knowing about below): in a single instant, this pressure lowers the stock by 1.5 model units, far short of its collapse point, so the stock does not pass its effect on — and the stock is the only route from the pressure to income. For the same reason, Catch decline and Conflict with Indian fishermen only show what arrives through their second route, Fleet motorization. The State triggers table under the results says so explicitly: Fish stock (CPUE), threshold 85 (either way), deviation −1.5, closed before and after the response.

Notice this network has no loop at all. No Impact here links back to either Response — unlike the app's other example networks. The sufficiency reading doesn't need one: the propagated effect above is still well-defined, which is exactly the point of building it this way. A response doesn't need to create a feedback loop for its effects to matter — and, as the table above shows, a response can be a clean, unambiguous success on the one thing it targets, while four other things get worse around it entirely on their own.

How confident is that, response by response?

Evaluated alone at full strength against the same pressure scenario, neither aid program ever neutralizes Catch decline, Conflict with Indian fishermen, Traditional fishing decline or Loss of traditional culture in any of 300 simulations that resample edge strengths within their uncertainty ranges — 0% for all four, consistent with the response having no path to any of them. Against Fisher income loss both reach 100% — but read that with the previous paragraph in mind: in this instant there is nothing to neutralize, because the Fish stock trigger is closed. Whether the aid really holds income once the stock does collapse is a question for the temporal simulation below.

Reach

This is where the redesigned network reads most starkly: 1 factor reached, including 1 of 5 Impacts. Not "reached weakly" or "reached indirectly" — reached, full stop, and only that one. No strength can ever make either aid program touch Catch decline, Conflict with Indian fishermen, Traditional fishing decline, or Loss of traditional culture, because there is no edge, direct or indirect, from either Response node into anything but Fisher income loss. That's not a limitation of the analysis; it's the network telling you, precisely and quantitatively, what this response can and cannot possibly influence, independent of magnitude — a response can be perfectly targeted and still leave 80% of a system's problems completely unaddressed, simply because nothing connects it to them.

Temporal simulation: does "Yes" last?

The sufficiency reading above is a single instant — everything happening at once, and by that reading, Fisher income loss is a clean success. Open Show temporal simulation across discrete time windows. With the defaults (both pushes added every window, run until neutralized) the answer is quick: neutralized at window 7 — an aid program renewed every window keeps up. But the aid was a single delivery, not a recurring program. So also check the pressure box for Number of fishers and boats at around 30% — representing that independent growth trend actually happening, in parallel, alongside population and demand — and set Response to Applied once and held. Fisher income loss starts strong — through window 5 the pressure hasn't reached it yet (baseline 0) and the aid already pushes it below zero (−9.0); at window 6, when the pressure arrives, it is within 5% of the baseline (0.53 against 11.78, "Neutralized (relative)") — but from window 7 the gap steadily narrows: net is 90% of the baseline at window 10 and 97% at window 15. The aid never reverses and never actually makes income loss worse; it simply has a fixed, one-time effect against a driver (the growing fleet) that keeps compounding every window, so its relative contribution fades toward irrelevance without ever crossing back to "worse than doing nothing." The other four — Catch decline, Conflict with Indian fishermen, Traditional fishing decline, and Loss of traditional culture — are all identical between baseline and net, at every single window, and they all grow (Traditional fishing decline and Loss of traditional culture used to have a zero baseline in the network's earlier design, when the aid still had a side channel into fleet motorization; now that channel is gone, they're driven by the same pressure trend as everything else, so they're never zero once fishing effort starts moving fleet motorization). The chart below plots exactly this: four panels turning red in lockstep — Net overlapping the baseline the whole way, never dipping into the shaded neutralized zone — while Fisher income loss starts green (Neutralized, then Improved beyond neutral through window 5, light green at window 6), turns amber (Partial) from window 7 onward, and stays amber through window 15 — the gap keeps narrowing, but within this run it never actually closes back to "as bad as no response."

Why the numbers grow so fast. This network's feedback paths aren't damped enough to settle down within 15 windows (population, demand, and the fishers/boats trend all keep compounding every window) — by design, so the shape of the trend is visible within a short, readable table. Treat this as a demonstration of direction and relative comparison (is the gap closing or opening? is a row identical across both columns or not?), not a forecast of real catch numbers over real years.

A threshold worth knowing about

The Fish stock factor has a threshold: an initial level of 100 and a threshold level of 85, in either direction (this file predates threshold directions; its old setting, 0.15 of the reference, was converted on load). Once the stock has moved 15 units, all three of its outgoing links — to Catch decline, Fisher income loss, and Conflict with Indian fishermen — switch on together, instead of each scaling from the very first unit of decline. That's a real fisheries phenomenon (a collapse threshold), and setting it on the State factor itself keeps all three targets waiting for the same collapse point.

The static reading and the temporal simulation disagree here, and on purpose. In a single instant the pressure moves the stock by 1.5 units, so the trigger stays closed and the sufficiency table shows no worsening of income at all. Window after window, though, the deviation accumulates (the stock has little self-regulation), and it crosses the 15 units at window 7 with the defaults (window 6 in the scenario with the fleet trend) — only then does income loss start to move. This is exactly the case the Trigger criterion setting is for: by the default, accumulated State level, a weak but steady pressure can still cross a threshold; by load arriving at the State, only what arrives within one window counts. Choose Compare both to see the windows where the two disagree. The table Change relative to initial values shows the stock in its own units (starting at 100) and the window in which the threshold was crossed.

Because the stock has no typical variation (SD) set, its threshold is measured in model units (15 units = 15 standard deviations of the model). Give a factor its typical variation in the node form (the SD, or a coefficient of variation) and its threshold, initial level and pushes are all read in real units.

The threshold's effect shows up unevenly in the table above, though, and that's worth understanding rather than mistaking for an inconsistency: Catch decline and Conflict with Indian fishermen each have a second, ungated route in — from Fleet motorization, which has no threshold of its own — so both are already moving by window 4 from that route alone. Fisher income loss has no such alternative; the Fish stock link is its only route in, so its baseline stays at exactly zero through window 5 and only starts moving at window 6, the moment Fish stock's own threshold is finally crossed.

Don't lose your work

Saving and resuming

Save savepoint (.idpsir.json) sits at the bottom of every step of the wizard — one file holding your schema, nodes, edges and layout, plus the scenario currently set up on the Scenarios tab (with its temporal settings). Reload it later from the Start step's Load savepoint option to pick up exactly where you left off. Scenarios you've saved during a session are not included yet — they live only until you close the app. A savepoint from an older version of the app is converted to standardized strengths on load, keeping its static results exactly the same.

Reference

Quick glossary

Driver
An underlying human activity or need, e.g. urban growth, tourism, agriculture.
Pressure
What that activity puts on the environment, e.g. wastewater discharge, overfishing.
State
The resulting condition of the environment, e.g. water quality, fish stock levels. Convention: name it as a neutral measurement ("Fish stock", not "Fish stock decline") — the direction (good/bad) belongs on the edges, see Modeling convention.
Impact
The consequence of that state, e.g. biodiversity loss, public health risk.
Response
A policy or management action addressing any earlier stage in the chain.
Density
How many of the possible connections in the network actually exist — higher means a more tightly linked system.
Centrality
A family of scores for "how important is this node," measured in different ways (see Metrics above).
Community
A cluster of nodes more connected to each other than to the rest of the network.
Sufficiency
Whether a response scenario's mitigation on an Impact is enough to neutralize a pressure scenario's worsening — the primary Scenarios reading, always well-defined regardless of the network's structure.
Neutralized
An Impact's net effect (worsening + mitigation) is zero or negative — the response fully covers the pressure's worsening on that Impact. A positive net, even a small one, means "No."
Temporal simulation
An optional reading that runs a scenario forward window by window (discrete time steps) instead of reading a single instant — useful for seeing whether a response's benefit holds up or erodes over time.
Verdict
The temporal simulation's per-window label for an Impact — Neutralized, Improved beyond neutral, Partial, or Failure/worsened — judged by the sign of the net's value, not its size. Not the same thing as sufficiency's "Neutralized" above; see Reading the Verdict.
Strength (beta)
How many standard deviations an edge's target changes when its source changes by one. Entered as a value, as r², or as a class (Weak 0.15 / Moderate 0.45 / Strong 0.80).
Self-regulation
The share of a factor's deviation that fades by itself each window (default 0.5) — e.g. a habitat that recovers. Only affects the optional temporal simulation, not the main sufficiency reading. See Self-regulation.
Priority
Relevance of an Impact (its social value × how much the pressure moves it × how reliable that prediction is) times the share of its worsening the response leaves uncovered.
Reach
How many factors — and how many Impacts — a response's influence can touch by following the network's links, independent of both the sufficiency and temporal readings.
