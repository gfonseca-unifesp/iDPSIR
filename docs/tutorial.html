Tutorial · iDPSIR

Finding your way around iDPSIR

iDPSIR is an R/Shiny app for building and reading causal networks under the DPSIR model — Driver, Pressure, State, Impact, Response — a framework environmental managers use to trace how a human activity turns into an environmental pressure, changes a system's state, causes an impact, and is met with a response. This walks through opening the app, filling in the wizard, and reading what each tab is telling you. No graph-theory background required.

Before you start

Running the app

Pick whichever of these matches what you're doing today — a one-off look, or ongoing work you'll want to keep and update.

Quick look, no setup

Runs the current main branch straight from GitHub. Nothing is kept on disk after you close R.

shiny::runGitHub("iDPSIR", "gfonseca-unifesp", "main")

Keep a working copy

Clones the repo so you can update it later and it opens cleanly as an RStudio project.

git clone https://github.com/gfonseca-unifesp/iDPSIR.git
cd iDPSIR

Then in RStudio: File → Open Project…, and run:

shiny::runApp()
Requires R ≥ 4.1. Missing packages are installed automatically on first run — no manual install.packages() step needed. Both routes open a browser tab with the app running locally — nothing is sent anywhere else.

Model

This is the DPSIR schema — the five categories, the order they connect in, and how each is drawn. The default is what almost everyone should use as-is; it's shown here so the colors and shapes below make sense everywhere else in the app.

CategoryOrderConnects forward toRole
Driver1Pressuredriver
Pressure2Statepressure
State3Impactstate
Impact4Responseimpact
Response5Driver, Pressure, State, Impactfeedback

Response is marked feedback: it's the only category allowed to connect back to earlier ones — the loop that makes a response actually change the system it responds to. "Advanced" options here let you swap the color palette or add extra levels, but most projects won't need them.

Add level asks for a name, a role and where to insert it. The role tells the engine what the level's factors are: one of the five above (two levels can share a role — e.g. a "Global driver" level before "Driver", both drivers) or a custom role such as a sub-driver, which sits in the chain (each level still connects only to the next one) but is none of the five. The levels after it move down one, so the order always stays valid. Remove selected level deletes a level that has no factors; a warning appears if no level plays one of the five roles.

Nodes

Growth rate and ceilingOptional, default 0 / blank. Used to prioritize Impacts on the Scenarios tab.

4

Edges

An edge is a directed link, from one node to another — it has to follow the connection order from the Model step (a Pressure→Impact edge, skipping State, will be flagged in Review).

FieldWhat it means
StrengthHow many standard deviations the target changes when this factor changes by one (a standardized path coefficient, beta). No data? Pick a class — Weak (0.15), Moderate (0.45, the default) or Strong (0.80). With data, choose "I have a value" and enter beta — or r² instead (the form uses |beta| = √r²), optionally with the sample size n. Drawn as line thickness on the graph.
Uncertainty rangeLowest and highest plausible strength. Optional: otherwise it comes from r² and n, or from the class (Weak 0–0.3, Moderate 0.3–0.6, Strong 0.6–1.0). Used only by the confidence readings, never to shrink the effect. A wide range is drawn dashed.
interaction_typepositive (the link increases its target) or negative (it decreases/mitigates it) — colors the edge red or green and appears in its tooltip.
evidence_typee.g. observational, expert_assessment, monitoring — where the link comes from, shown on hover.
referenceOptional — a DOI, URL, or plain citation backing this specific link. Shown on hover and, if you check "Edge references" on the Report tab, listed in a References section so a reader can trace any prediction back to its evidence.
What you need to enter. Only the structure (nodes with their category, edges) and the sign of each edge are required. Everything else has a default, and the network runs with them — the results are then qualitative, and the Review step and the report say how many edges rely on a default. Fields that do the same job replace each other; fill in one: strength = beta, or r², or a class (default Moderate); uncertainty = a range, or r² with n, or the range of the class. The effect of a scenario is the product of the strengths along each causal path, summed over paths — a response far from an Impact is naturally attenuated. If the network's feedback loops would amplify without bound, Build is blocked and the message names the edges on the loop.
5

Review and build

A summary ("6 nodes, 7 edges") plus a plain-language list of anything invalid — usually an edge that skips a category. Fix those, then press Build/Rebuild graph. This is also the button to press again any time you go back and edit nodes or edges — the Explore tabs always show the graph as of the last build, not your unsaved edits.

Nothing updates automatically. Changed a node's category after building? Rebuild before trusting what Explore shows you.

The Explore tabs

Scenarios

Tests "what if we implemented this response, and how hard?" — without touching your saved network. Two independent "pushes" you build side by side: what's pushing the system to get worse, and how you're responding to it.

GraphScenariosMetricsReport
Pressure scenariocheckbox + slider each

Optional. One row per Driver/Pressure node — turn on any combination you expect to worsen, and how strongly. A push of 100% is one standard deviation of that factor; the slider goes up to 500%, and a factor with a typical variation (SD) also takes the push in its own units ("or, in units").

Response scenariocheckbox + slider each

One row per Response node — turn on any combination you want to test, and how strongly each is implemented.

Apply scenariobutton

Runs both scenarios and shows "Is the response enough? (sufficiency)" — for each Impact, how much the pressure scenario worsens it, how much the response scenario mitigates (or, sometimes, worsens) it, whether that's enough to neutralize the worsening, and how strong the response would need to be if not. The effect is the product of the edges' strengths along each causal path, summed over paths. Simulations (confidence) (100, 300 or 1000) sets how many resamples the confidence and prioritization tables use — fewer is faster, more gives steadier percentages.

How confident is that, response by response?table

Every response in the network, evaluated alone at full strength against the same pressure scenario: the percentage of simulations — resampling every edge's strength within its uncertainty range — in which that response alone neutralizes each Impact. A first row, Planned scenario (as set), does the same for the scenario exactly as configured with the sliders — the confidence of the verdict shown in the sufficiency table. Impacts the pressure does not reach show "—".

State triggerstable, only with thresholds

Each State with a threshold: its deviation under the pressure alone and with the response, whether its trigger is open before and after, and whether the response closes it. A closed trigger holds back everything beyond that State — which is why an Impact can be neutralized "by the trigger" rather than by mitigation, and why Reach also reports how many factors this scenario actually reaches.

Impact prioritizationtable + chart

Which Impact to act on first. Relevance = value v × importance D (how much the pressure scenario moves that Impact, relative to the most affected one) × reliability (how often that prediction keeps its sign when every strength is resampled within its range). Priority = relevance × gap (the share of the worsening the response scenario leaves uncovered — 0 when neutralized). An Impact the pressure doesn't worsen reads "Not affected". Downloadable as CSV and included in the report.

Reachtable

How many factors — and how many Impacts — the active response(s) can touch by following the network's links. Independent of the sufficiency reading above: it's a plain count of what's reachable, always available.

Show temporal simulation across discrete time windowsoptional

Runs the same two scenarios forward window by window instead of reading a single instant (click Run simulation after changing any of its settings) — useful when a response might, windows later, become a new pressure itself (see the worked example). Pressure and response each run as Added every window (default), Applied once and held (window 1 only; the level it creates fades only through self-regulation) or For a number of windows (a start window and a duration per factor — e.g. an aid programme that ran for five years). When a factor has a growth rate, Apply growth trends even to factors outside the pressure scenario (on by default) moves its base level in both runs, and Edge intensity by window shows what each link out of a growing factor or a thresholded State passes on in each window (downloadable as CSV). Simulation length: until the response neutralizes the Impact (default, up to 50 windows — it stops at the first window in which every Impact the response reaches, and that is worsened in either run, is at or below zero or within the neutralization tolerance of its baseline; otherwise it says "Not neutralized within N windows") or a fixed number of windows; with a growing trend a neutralization may not last, so Continue after neutralizing keeps running N more windows. Optional: a neutralization tolerance (default 5% of the baseline; a net value at or below it is labelled "Neutralized (relative)" and counts as neutralized for the stop — set 0 to require zero), and a baseline without any response (ignoring Impact → Response links). With a thresholded State, a Trigger criterion: accumulated State level (default — has the State deviated beyond the critical point, adding up every window?), load arriving at the State (did what arrived in this window pass the limit?), or compare both; a table then shows each trigger open or closed window by window. Factors with an initial level get a Change relative to initial values table, in their own units, with the window in which a threshold was crossed. A progress indicator shows "Window X of N" while it computes. Shows a table of how each Impact changes window by window, with a Verdict per row (see Reading the Verdict), and a chart — one panel per Impact, dashed baseline vs. solid Net, each Net point colored by that window's Verdict, with the neutralized zone (Net ≤ 0) shaded — downloadable as PNG or SVG and included as a figure if this scenario is added to the report.

Read this before your first network

Modeling convention: orienting nodes and reading signs

The app never guesses whether "more" of a factor is good or bad — that's a decision you make when you name a node and sign its edges. Get this right and consistent, and every reading downstream (sufficiency, confidence, temporal Verdict, the temporal chart's colors) is trustworthy. Get it inconsistent, and a table can report the opposite of what you intended without any error or warning — the app validates that a sign is positive or negative, not that it means what you think it means.

Step 1 — orient each node: decide what "more" means

CategoryWhat "more" meansExample
Driver / PressureMore force or stress — more is more pressure.fishing effort, population growth
StateThe condition itself, measured in its natural/good sense — more is a better condition.Coral cover, Fish stock, Biodiversity — never Coral degradation or Fish stock decline
ImpactThe problem or damage itself — more is worse.Catch decline, Fisher income loss

State is the one category worth pausing on: name it as a neutral measurement, not as the problem it's usually associated with. A State named after a problem ("Fish stock decline") quietly bakes a sign assumption into the node itself — one that can silently drift out of sync with whatever the edges actually say.

Step 2 — the edge's sign is mechanical

Once every node is oriented, signing an edge is a small, mechanical question: when the source goes up, does the target go up (positive) or down (negative)? Nothing about "good" or "bad" enters at this step — that judgment already happened in Step 1, when you chose what "more" means for each node. With the standard orientation above, the connections this app's schema allows always sign the same way:

LinkSignWhy
Driver → Pressurepositivemore force → more pressure
Pressure → Statenegativethe pressure reduces the good condition
State → Impactnegativemore good condition → less of the problem
Response → Driver / Pressurenegativethe response reduces the force/pressure
Response → Statepositivethe response improves the condition
Response → Impactnegativethe response reduces the problem
Golden rule: the same node uses the same orientation on every one of its edges — incoming and outgoing alike. Almost every sign mistake in a DPSIR network comes from breaking this rule: signing a State as "good" on its incoming edge and as "the problem" on its outgoing edge (or vice versa). See sample_nodes.csv/sample_edges.csv's own history for a worked example of exactly this mistake, and the Mangi network below for what a consistent, neutral State looks like in practice.

Reading the Verdict (temporal simulation)

With an Impact oriented as the problem (Step 1 above): zero means no deviation from doing nothing, a positive value means worse, and a negative value means better than doing nothing — the response didn't just help, it pushed the factor past neutral. Each simulated window compares the baseline (pressure only) against the net (pressure and response together, the same "Net" column the sufficiency table above already uses for this quantity) and labels the Impact's net value accordingly:

VerdictConditionMeaning
Not affectedbaseline ≈ 0 and net ≈ 0the pressure has not reached this Impact (yet) — nothing to neutralize. Window 0 shows "—". The sufficiency table uses the same label when the pressure does not reach an Impact in a single instant; such Impacts stay out of the confidence and the prioritization
Neutralizednet ≈ 0the response's benefit exactly offsets the pressure's worsening
Improved beyond neutralnet < 0the response did more than enough — the factor is better than if nothing had happened at all
Neutralized (relative)0 < net ≤ tolerance × baselinepractically neutralized: within the tolerance (default 5%) of the baseline. "Until neutralized" stops here too; a tolerance of 0 turns the label off
Partial0 < net < baselinestill a problem, but smaller than it would be without the response
Failure/worsenednet ≥ baselineas bad as, or worse than, no response at all

The Verdict is judged by sign, not by how large a number is — a response that overshoots into strongly negative territory is Improved beyond neutral, never Failure/worsened, no matter how big that negative number gets. This also keeps the label consistent with the temporal chart's color: green always means neutralized or better (net ≤ 0), so a row marked worse can never show up green.

Temporal simulation

Self-regulation: how a factor recovers on its own

self_regulation (0–1, default 0.5) is the share of a factor's deviation that fades by itself each window, independently of the network: 0 = nothing fades and everything that arrives accumulates (a stock with no replenishment, a persistent contaminant); 0.3 = 30% of the deviation fades each window (a population rebuilding, a habitat regenerating); 1 = no memory, the factor only reflects what arrives in the current window.

Each window: new value = (1 − self_regulation) × previous value + what arrives through the edges + the push.

Example — fishing effort (P) → fish stock (S) → catch decline (I), with strengths 0.7 and 0.6 (both negative) and a pressure of 1 standard deviation:

CaseWindow 24812
Ongoing pressure, self-regulation 0 everywhere — fish stock−0.70−4.20−19.6−46.2
Ongoing pressure, stock recovers 30% per window — fish stock−0.70−1.53−2.14−2.29 (settles at −0.7 ÷ 0.3 = −2.33)
Ongoing pressure, self-regulation 1 everywhere — fish stock−0.70−0.70−0.70−0.70 (same as the static reading)
One-off pressure, stock recovers 30% per window — fish stock−0.70−0.34−0.08−0.02 (back to normal)

Under a constant load, a factor settles at load ÷ self-regulation: a contaminant with self-regulation 0.05 accumulates up to 20 times what arrives each window, which is how a small per-window pressure can still cross a threshold through accumulation.

Self-regulationHalf-life of recoveryBuild-up at equilibriumTypical of
0.0513.5 windows20×contaminant in sediment
0.106.6 windows10×reef recovery, long-lived species
0.301.9 windows3×short-cycle fish stock
0.50 (default)1 window2×water quality that renews quickly
1—1×monthly income, catch in the window

What makes an Impact converge is the chain's self-regulation; the response mode decides the effort; the stop criterion says in which window the problem was solved.

Four networks, four purposes

Example networks

Four ready-to-load networks ship with the app, each making a different point. Start with whichever matches what you need right now — a five-minute orientation, a real published network, the deepest example in the app, or a didactic case on prioritizing responses (the last two are covered in full in their own sections).

Fisheries — the smallest possible loop

Five nodes, five edges, one closed feedback loop: Coastal tourism growth (Driver) → Overfishing (Pressure) → Fish stock (State) → Fisher income loss (Impact) → Fishing quota policy (Response) → back to Coastal tourism growth. No subsystem filters, no temporal simulation needed to see what's going on — this is the network to open first, just to get oriented with the wizard and the Graph/Scenarios tabs before anything else adds complexity. Turn on Coastal tourism growth as pressure and Fishing quota policy as response, both at 100%: because it's a genuine loop, the response's Reach covers all 4 other factors — but with this network's edge strengths (three Strong links along the pressure chain, a Moderate Impact → Response link and a Weak Response → Driver link), a single response this far from the Impact isn't remotely enough on its own (Fisher income loss needs 667% strength to neutralize a 0.495 worsening with only -0.074 of mitigation) — a quick, honest first look at what "Strength needed" means when a response is badly outmatched.

Mangi et al. 2007 — a real published network, and a real bug it caught

18 nodes, 31 edges — coral-reef fisheries management in a real paper (Mangi, S.C., Roberts, C.M., & Rodwell, L.D. (2007). Reef fisheries management in Kenya: Preliminary approach using the driver-pressure-state- impacts-response (DPSIR) scheme of indicators. Ocean & Coastal Management, 50(5-6), 463-480, doi:10.1016/j.ocecoaman.2006.10.003). This is the network that caught a real, reproducible bug during development: the older equilibrium-based reading this app used to show (removed since, see Scenarios above) reported Gear restrictions as making Reef ecosystem degradation worse — the wrong sign for a response explicitly meant to protect the reef. Loading this network and applying pressure from Coastal population growth + Market demand for reef fish, with Gear restrictions as the response, shows the corrected sufficiency reading: Reef ecosystem degradation reads worsening 0.03 / mitigation -0.069 / net -0.039, Yes, neutralized at 44% strength — mitigation with the right sign, not the wrong one. It's also a good look at a densely cross-linked network: this single response's Reach covers 14 of the other 17 factors, because Responses here loop back into several Drivers, Pressures and States at once, not just the one Impact they're aimed at.

This network is also the concrete illustration of the modeling convention above: every State is a neutral measurement — Fish stock, Coral cover, Biodiversity — never pre-judged as "decline" or "degradation", so Pressure→State and State→Impact are both negative and Response→State is positive, exactly the standard signing from Step 2 above.

Worked example: the aid that became a pressure

This network is built from a published study — Gnanapragasam, Ratnasiri & Fleming 2026, Marine Policy 189, 107095, on Sri Lanka's small-scale fisheries — and parametrized from its own numbers: 32 years of fishing effort, a Gordon-Schaefer model of the stock, and the effort cuts it recommends. One window is one year, starting in 2004. It shows the three things the temporal simulation adds to the static reading: growth trends, pushes that last a set number of years, and a threshold crossed by accumulation.

Where every number comes from

What comes from the paper and what does not. From the paper: the effort series, the effort → stock strength (r² = 0.68), the stock benchmarks (MSY, MEY, BMSY), the growth of fish demand and its 2016 peak, the aid periods and the effort cuts. Derived from it: the stock's scale and SD (from the Gordon-Schaefer equilibrium) and the two aid strengths, calibrated so the simulated effort follows the observed one. Not in the paper: population growth (national statistics) and the links the paper describes only qualitatively, which use the app's strength classes. Read it as a structured, checkable interpretation of the study, not as the study's own model.

The story

Fishing effort in Sri Lanka rose 130% between 1990 and 2021. The paper traces most of it to livelihood aid: after the 2004 tsunami (2005–2009) and the end of the civil war (2010–2012), donors replaced — and over-replaced — boats and gear. The aid was meant to restore fishers' income, and it did; it also grew the fleet, the fleet's effort pushed the stock below the level of maximum sustainable yield, and catches fell from 2014. The paper's own answer is an effort-based quota: 5% less effort brings it to MSY, 25% to the economic optimum (MEY). Illegal trawling by Indian boats adds pressure throughout.

Two choices are worth knowing. States whose strengths come from an equilibrium relationship (the Schaefer stock, the motorized share) keep self-regulation 1: in the temporal simulation a link passes its strength every window, and a factor with self-regulation s settles at strength ÷ s, so anything below 1 would inflate them. And the stock's threshold is BMSY, from the paper; the usual collapse limit (half of BMSY, a management convention) was tried first and is never crossed at realistic levels, so the stock would never reach its Impacts. One State breaks the neutral-name default on purpose: Fleet motorization is oriented "more is worse" (more motorized capacity is more pressure), so all its links are positive — still consistent with the golden rule, since the orientation holds for every one of its links.

Growth: the world moves even outside the scenario

Three factors have a growth rate: population (+0.8%/year), per-capita demand (+2.3%/year) and fleet capacity (+1%/year). None of them is in the pressure scenario, yet their base level moves in both runs — with and without the response — because Apply growth trends even to factors outside the pressure scenario is ticked. Demand stops at its 31 kg ceiling in 2017 (window 13): in Edge intensity by window, the link demand → effort grows 0.010, 0.021 … then stays at 0.144. That table is the place to see growth at work: each link out of a growing factor passes a little more every window, in proportion to (1 + growth rate), never compounding twice.

Growth is not self-regulation. Self-regulation is how a deviation caused by the network fades; growth is how the factor's own base level moves by itself. Because the trend is the same with and without the response, it does not change the difference between the two runs — unless it pushes a State across its threshold.

A threshold worth knowing about

Apply the scenario and look at the static State triggers table: Fish stock (biomass), threshold 345 kt (falling) = −1.46 SD, deviation −0.36 with the pressure alone, closed before and after. In a single instant, illegal trawling does not overfish the stock — so the static reading shows no worsening for any Impact — every row reads Not affected. The problem only appears over time: the fleet's effort accumulates year after year, the stock crosses BMSY in 2012, and from then on the stock's effects switch on. This is the case the Trigger criterion exists for: by accumulated level (the default) the trigger opens; a single window's load never gets there.

Try the paper's smallest option: give the quota 827 thousand kW-days (the 5% cut that brings effort to MSY) in its or, in units field, instead of the 85% slider. The stock only reaches about 327 kt by 2030 — still below BMSY — and the trigger stays open; with anti-poaching too it reaches about 345 kt, right at the threshold. The paper's own conclusion — a modest cut is a start, the MEY cut restores the stock — comes out of the model.

Worked example: which response, and when?

A port has three things going on at once, and a limited budget. This didactic network shows how the app turns that into a decision: the prioritization says which Impact to deal with first — weighing how much each one matters, not only how much it worsens — and the temporal simulation says when each response has to be active.

Download the example

Load it on the Start step (Load savepoint). Scenario 1 is set up, and four scenarios are already saved (they are rebuilt when you build the graph).

example_port.idpsir.json
Illustrative, not a real assessment. The structure comes from a port environmental impact table; every strength is a class (weak, moderate, strong), so the numbers are qualitative. The relevance values are examples of what a stakeholder elicitation (swing weights) might give.

The story

Two groups of Impacts run through the same port:

  • Turbidity — maintenance dredging and ship traffic put sediment back in suspension, the water turns turbid, fauna changes its behaviour and phytoplankton loses light (primary production). Turbidity clears within a season or two (self-regulation 0.7).
  • Metals — rain washes the cargo terminal, and the runoff carries dissolved zinc and copper, which contaminate fish and shellfish and push the water out of its CONAMA quality class. Metals persist (0.2) and biota accumulates them (0.1).

Three responses are available: a runoff treatment system (acts on the metals), an environmental work window that restricts dredging to the least sensitive period (acts on turbidity), and generic best practices (a little of both, weakly). Dredging happens in a campaign (windows 3 to 5); runoff and traffic never stop.

When: one response has a season, the other has no end

Open Temporal simulation, tick Show temporal simulation and click Run simulation. Pressure and response run For a number of windows: dredging in windows 3–5, runoff and traffic always. Compare the saved scenarios on the Report tab (include the temporal simulation):

  • 3. + Work window during dredging — the work window is active only in windows 3–5, yet fauna behaviour peaks at 0.29 instead of 1.55 without any response, and returns to zero after the campaign. Keeping it all year only pushes the factors "beyond neutral": effort with no remaining problem to solve.
  • 4. Runoff treatment starts late — the same responses, but the runoff treatment only from window 6. The seafood contamination climbs to about 10 and stays there (about 0.1 when the treatment starts in window 1): contamination accumulates in the biota, so this response has to start early and never stop.

The lesson the network gives, in one line: fund the runoff treatment first and keep it running; add the work window only for the dredging campaigns — and leave primary production as the last concern, not because it is small, but because it weighs less.

Don't lose your work

Saving and resuming

Save savepoint (.idpsir.json) sits at the bottom of every step of the wizard — one file holding your schema, nodes, edges and layout, plus the scenario currently set up on the Scenarios tab (with its temporal settings). Reload it later from the Start step's Load savepoint option to pick up exactly where you left off. The scenarios you saved are included too (their settings, not their results): they are recomputed after you build the graph, and appear again under Saved scenarios and on the Report tab. A savepoint from an older version of the app is converted to standardized strengths on load, keeping its static results exactly the same.

Reference

Quick glossary

Driver
An underlying human activity or need, e.g. urban growth, tourism, agriculture.
Pressure
What that activity puts on the environment, e.g. wastewater discharge, overfishing.
State
The resulting condition of the environment, e.g. water quality, fish stock levels. Convention: name it as a neutral measurement ("Fish stock", not "Fish stock decline") — the direction (good/bad) belongs on the edges, see Modeling convention.
Impact
The consequence of that state, e.g. biodiversity loss, public health risk.
Response
A policy or management action addressing any earlier stage in the chain.
Density
How many of the possible connections in the network actually exist — higher means a more tightly linked system.
Centrality
A family of scores for "how important is this node," measured in different ways (see Metrics above).
Community
A cluster of nodes more connected to each other than to the rest of the network.
Sufficiency
Whether a response scenario's mitigation on an Impact is enough to neutralize a pressure scenario's worsening — the primary Scenarios reading, always well-defined regardless of the network's structure.
Neutralized
An Impact's net effect (worsening + mitigation) is zero or negative — the response fully covers the pressure's worsening on that Impact. A positive net, even a small one, means "No." When the pressure does not reach the Impact at all, the verdict is Not affected instead.
Temporal simulation
An optional reading that runs a scenario forward window by window (discrete time steps) instead of reading a single instant — useful for seeing whether a response's benefit holds up or erodes over time.
Verdict
The temporal simulation's per-window label for an Impact — Not affected, Neutralized, Improved beyond neutral, Neutralized (relative), Partial, or Failure/worsened — judged by the sign of the net's value, not its size. Not the same thing as sufficiency's "Neutralized" above; see Reading the Verdict.
Strength (beta)
How many standard deviations an edge's target changes when its source changes by one. Entered as a value, as r², or as a class (Weak 0.15 / Moderate 0.45 / Strong 0.80).
Self-regulation
The share of a factor's deviation that fades by itself each window (default 0.5) — e.g. a habitat that recovers. Only affects the optional temporal simulation, not the main sufficiency reading. See Self-regulation.
Priority
Relevance of an Impact (its social value × how much the pressure moves it × how reliable that prediction is) times the share of its worsening the response leaves uncovered.
Reach
How many factors — and how many Impacts — a response's influence can touch by following the network's links, independent of both the sufficiency and temporal readings.
